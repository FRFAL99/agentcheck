# agentcheck

> Working name. Find out in a few seconds whether you can trust what Claude Code just did in your
> repo.

> This is the **product spec**: what the tool is and why. It changes rarely. Where we are today is
> in [docs/STATUS.md](docs/STATUS.md); how the work is organised is in [CLAUDE.md](CLAUDE.md). Where
> a plan has refined a point of this spec after reading the official documentation, the section
> says so and links to the decision.

## 1. The problem

A developer working alone with coding agents (Claude Code first and foremost) produces far more
changes than they can carefully reread. Existing AI code review tools (CodeRabbit, Greptile, Qodo,
etc.) are built for teams, work on pull requests, are priced per developer and produce a lot of
comments, often noisy.

What is missing is a tool built for the solo developer that, at the end of every agent turn,
answers one question only: **can I trust what was done, or do I need to look at something?**

## 2. The idea

`agentcheck` hooks into Claude Code through hooks. At the end of every turn it:

1. reads the repo diff against the start of the session;
2. reads what the agent said in the session;
3. compares **what the agent says it did** with **what it actually did**;
4. produces a very short report with only the things that deserve attention;
5. remembers over time which problems recur and which findings you ignore, to reduce noise.

The differentiator against existing tools is point 3: they only see the diff, `agentcheck` also
sees the agent's claims.

## 3. Design principles

- **Deterministic first, LLM second.** Anything that can be detected with ordinary code is detected
  with ordinary code. The LLM steps in only on ambiguous parts and on already-reduced input.
- **Low noise.** At most 5–8 lines per report. No style comments. If there is nothing relevant, the
  report just says everything is fine.
- **Fast.** The deterministic analysis must complete in under 2 seconds on a typical diff. LLM calls
  must not block the flow for more than a few seconds.
- **Never modify the user's code.** The tool observes and reports; fixes are made by the agent or
  the developer. This extends to the user's git state: index, refs, stash and working tree — see
  [ADR 0001](docs/adr/0001-never-touch-the-users-git-state.md).
- **Local data.** Memory and logs stay in the repo (`.agentcheck/`). Only LLM calls leave the
  machine.

## 4. Architecture

```
Claude Code
   │  SessionStart hook  → saves the baseline (starting commit/snapshot)
   │  Stop hook          → runs the analysis
   ▼
agentcheck
   ├── collector     reads hook input, git diff, transcript
   ├── structural    deterministic structural diff (tree-sitter)
   ├── claims        extracts and verifies the agent's claims (LLM)
   ├── risk          risk score from structural signals + claims
   ├── memory        SQLite: finding history, feedback, calibration
   └── report        short terminal output + markdown log
```

### 4.1 Hooking into Claude Code

Configuration in the repo's `.claude/settings.json`, generated by `agentcheck init`:

```json
{
  "hooks": {
    "SessionStart": [
      { "hooks": [{ "type": "command", "command": "agentcheck hook session-start" }] }
    ],
    "Stop": [{ "hooks": [{ "type": "command", "command": "agentcheck hook stop" }] }]
  }
}
```

Hooks receive JSON on stdin that includes, among others, `session_id`, `transcript_path`, `cwd`
and, for `Stop`, `stop_hook_active` and `last_assistant_message`.

Important: `Stop` fires at the end of **every turn** of the agent, not only at the end of the
session. The diff must therefore be computed against the session baseline, and the report must
highlight what changed in the last turn.

> **Verified on 2026-09-24** against the official hooks reference — input format, available events,
> output format, `stop_hook_active`, and what is and isn't shown to the user. The facts, with what
> they change for this spec, are in
> [docs/knowledge/claude-code-hooks.md](docs/knowledge/claude-code-hooks.md).

### 4.2 Session baseline

On the `SessionStart` event:

- save `git rev-parse HEAD`;
- save a snapshot of the working tree with `git stash create` (creates a state commit without
  touching files; returns an empty string if the tree is clean, in which case the baseline is
  `HEAD`);
- record the list of untracked files (not included in `git stash create`).

Everything saved in `.agentcheck/sessions/<session_id>.json`.

> **Refined by [plan v1, decision 2](docs/plan-v1-every-turn-leaves-a-trace.md):** the snapshot is
> a git _tree_ written through a temporary index, which includes untracked files and is computed
> the same way at the start and at every turn. `git stash create` plus a separate untracked list
> would give two representations to reconcile.

### 4.3 Structural diff (deterministic)

`tree-sitter` parsing of the modified files, before and after. Signals to detect:

| Signal                          | Example                                                          | Indicative weight |
| ------------------------------- | ---------------------------------------------------------------- | ----------------- |
| Public signature changed        | parameters or return type of an exported function               | high              |
| Function removed                | exported function deleted                                        | high              |
| Code changed with no tests      | `src/` changes, `tests/` doesn't                                 | medium            |
| New dependency                  | line added in `requirements.txt`, `pyproject.toml`, `package.json` | medium          |
| Sensitive file touched          | `.env*`, migrations, CI workflows, auth config                   | high              |
| Import of a non-existent module | import not resolvable in the repo or its dependencies            | high              |
| Tests removed or disabled       | tests deleted, `skip`, `xfail`, `.only`                          | high              |
| Many files touched              | above a configurable threshold                                   | low               |

Languages supported in the MVP: **Python** and **TypeScript/JavaScript**. For other files the tool
reports file-level signals only.

### 4.4 Claim verification (LLM)

1. The final assistant messages of the current turn are extracted. The last one arrives directly in
   the Stop input as `last_assistant_message`; the transcript (JSONL) is only for earlier messages
   of the turn, and **may lag** — see
   [docs/knowledge/claude-code-hooks.md](docs/knowledge/claude-code-hooks.md).
2. An LLM call extracts the **verifiable claims** in structured form (JSON), for example: "I added
   tests for X", "I didn't change the public API", "I updated the documentation", "all tests pass".
3. Each claim is compared with the structural diff (not with the whole codebase) and classified as
   `verified`, `unverifiable` or `contradicted`.
4. Extra check only on functions whose body changed with an unchanged signature: the LLM receives
   the function before and after and flags likely undeclared behaviour changes.

Model: a cheap one (e.g. the Haiku family) for extraction and comparison. The model must be
configurable.

Claims such as "tests pass" can also be verified deterministically by searching the transcript for
the actual test run and its output.

### 4.5 Risk score

A simple, explainable combination of signals: weighted sum, with thresholds for `low`, `medium`,
`high`. Every score must be explainable by listing the signals that make it up. No opaque models.

### 4.6 Memory (SQLite)

File: `.agentcheck/agentcheck.db`.

Minimum tables:

- `sessions` (id, started_at, baseline_commit, baseline_snapshot)
- `turns` (id, session_id, completed_at, risk_level, files_touched)
- `findings` (id, turn_id, type, severity, file, symbol, message)
- `feedback` (finding_id, outcome: `useful` | `false_positive` | `ignored`, date)

Use of memory:

- lower the severity of finding types often marked as false positives in that repo;
- highlight recurring patterns ("third time this week that files in `src/` are modified without
  touching tests");
- statistics with `agentcheck stats`.

### 4.7 Report

Example terminal output:

```
agentcheck · turn 4 · risk MEDIUM

✗ Contradicted: "I added tests for parse_invoice" → no test file modified
! Signature changed: api/invoices.py::create_invoice (new required parameter `currency`)
! New dependency: python-dateutil in pyproject.toml
✓ 3 claims verified

Details: agentcheck last
```

If there is nothing relevant: a single line (`agentcheck · turn 4 · all good`).

Every report is also saved in `.agentcheck/reports/<session_id>/<turn>.md`.

> **How it reaches the user:** a Stop hook's plain stdout goes to the debug log only. The report is
> delivered as the `systemMessage` field of a JSON object on stdout, which Claude Code shows to the
> user. Verified 2026-09-24, see the knowledge file.

### 4.8 "Send back to Claude" mode (optional)

If enabled in configuration and the risk is `high`, the `Stop` hook blocks the end of the turn and
passes to Claude, as the reason, the list of serious findings, so the agent can fix them.

Mandatory rules:

- if `stop_hook_active` is `true`, do not block again (avoids infinite loops);
- at most one send-back per turn;
- disabled by default.

## 5. Stack

- Python 3.11+, project managed with `uv`
- CLI: `typer`
- Parsing: `tree-sitter` with Python and TypeScript grammars
- LLM: official `anthropic` SDK, key from the `ANTHROPIC_API_KEY` environment variable
- Storage: standard library `sqlite3`
- Terminal output: `rich`
- Tests: `pytest`

## 7. CLI commands

| Command                            | What it does                                                   |
| ---------------------------------- | -------------------------------------------------------------- |
| `agentcheck init`                  | configures the hooks in `.claude/settings.json`, creates `.agentcheck/` |
| `agentcheck hook session-start`    | called by the hook, saves the baseline                         |
| `agentcheck hook stop`             | called by the hook, runs the analysis                          |
| `agentcheck last`                  | shows the full report of the last turn                         |
| `agentcheck mark <id> useful\|fp`  | records feedback on a finding                                  |
| `agentcheck stats`                 | statistics on findings and recurring patterns                  |
| `agentcheck run`                   | runs the analysis by hand, without hooks (useful for debugging) |

## 8. Configuration

File `.agentcheck/config.toml`:

```toml
[llm]
model = "claude-haiku-4-5"
enabled = true

[report]
max_lines = 8

[risk]
many_files_threshold = 15

[feedback_loop]
enabled = false
min_level = "high"

[paths]
sensitive = [".env*", "migrations/**", ".github/workflows/**"]
tests = ["tests/**", "**/*.test.ts", "**/test_*.py"]
```

## 10. Scope

### In

- Claude Code only
- git repositories only
- Python and TypeScript/JavaScript only for structural analysis
- Individual use from the terminal
- Structural diff, claim verification, short report, local memory

### Out (for now)

- Other agents (Cursor, Codex, etc.)
- GitHub/GitLab pull request integration
- Web dashboard, accounts, teams, payments
- Other languages
- Automatic code modification by the tool

## 11. Success metrics

After 2–3 weeks of real use:

- **Personal retention:** the tool is still active and hasn't been disabled out of annoyance.
- **Precision:** at least one finding in two is marked as useful.
- **Concrete value:** at least one documented case of a bug or false claim that would have gone
  unnoticed.
- **Speed:** deterministic analysis under 2 seconds, full report under 10 seconds.

## 12. Open questions

- Should the report be shown on every turn or only when the risk is above `low`?

## 13. Instructions for Claude Code (when working on this repo)

- Follow the phases in order; do not anticipate features from later phases.
- Every module must have tests with fixtures in `tests/fixtures/`.
- Do not introduce dependencies beyond those listed in section 5 without asking.
- Keep the deterministic analysis separate from LLM calls: `structural/` must never import
  `claims.py`.
- LLM calls must have a timeout, error handling and a fallback: if the LLM doesn't respond, the
  deterministic report is still produced.
- Before implementing hooks, verify input and output format against the official Claude Code
  documentation — done on 2026-09-24, re-check when the installed Claude Code version changes.
